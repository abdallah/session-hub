# Tasks implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Human-level tasks in sessionhub, proposed by agents and confirmed by you, viewable per day with todo carry-over.

**Architecture:** Three tables in schema v13 hold tasks, their state-change log, and session links. The day view replays the log up to the end of the requested day in the requested time zone. Agents reach it through four MCP tools that fail open into the offline queue; you reach it through `sessionhub task` and a dashboard **Tasks** tab.

**Tech Stack:** Go, SQLite (`internal/store`), net/http `ServeMux` patterns (`internal/server/routes.go`), the stdio MCP server (`internal/mcp`), the vanilla JS dashboard (`internal/server/dashboard/index.html`).

**Spec:** `docs/dev/superpowers/specs/2026-10-07-tasks-design.md`

## Global Constraints

- Task id: `t_` + 8 random bytes, base64url (no padding). Clients may supply one; the server accepts any id matching `^t_[A-Za-z0-9_-]{11}$`.
- `title` 1 to 200 runes; `ref` at most 200 runes; `ref_url` empty or http/https, at most 2000 bytes; `note` at most 500 runes. Trimmed; no control characters (reuse `checkText` in `internal/store`).
- `source` is one of `ticket`, `email`, `chat`, `other`.
- States: `proposed`, `todo`, `in_progress`, `done_proposed`, `done`, `dropped`.
- Actor strings: `web:<name>`, `machine:<name>`, `session:<id>`.
- A bad transition is `store.ErrConflict` → HTTP 409.
- Timestamps are UTC RFC 3339 with nanoseconds, as elsewhere in the store (`formatTS`, `parseTS`).
- Task event id (`EventID`): `te_` + 8 random bytes, base64url; a repeat is a no-op returning the current task.
- Every new route gets a case in `internal/server/auth_test.go`; the test walks `routes()` and fails on a missing case.
- Commit messages: imperative, sentence case, no Co-Authored-By trailer.

## Actor rule

The server decides who is acting, not the client:

- Session cookie → `web:<name>`, full rights ("you").
- Machine token and a non-empty `session_id` in the body → `session:<id>`, agent rights.
- Machine token without `session_id` → `machine:<name>`, full rights (the CLI).

Agent rights: create `proposed` only; `todo` → `in_progress` (only via link); `todo`|`in_progress` → `done_proposed`. Machine tokens are already trusted, so this is a workflow rule, not a security boundary.

## Review Focus

1. A queued `propose_task` replayed twice (queue retry after a timeout that actually succeeded) must create one task, not two.
2. An event at 23:30 local on day D must count for D in that zone, not for D+1 in UTC.
3. Merging a proposal into a task the session is already linked to must not fail on the `task_sessions` primary key.
4. `propose_done` on a task that is already `done` (agent out of date) must return a clear 409 message, and the MCP tool must report it to the agent rather than queue it.
5. A task reopened from `done` on day D+1 must still show in **Done** on day D's view.

Each has a test in the owning task below.
